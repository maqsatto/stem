# Тестирование и приёмка

## 1. Как запускать

### Backend

```bash
cd backend
uv sync --extra dev
uv run ruff check app tests
uv run pytest
```

Тестовая БД:

```bash
createuser -P mlstem
createdb -O mlstem mlstem_test
export DATABASE_URL=postgresql+psycopg://mlstem:mlstem@localhost:5432/mlstem_test
uv run pytest
```

Фикстуры пересоздают схему в тестовой БД. **Никогда не направляйте тесты на
`mlstem`**: данные будут удалены.

### Frontend

```bash
cd frontend
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build
```

Один раз:

```bash
make check
```

## 2. Текущие результаты

Проверено локально:

| Проверка | Результат |
|---|---|
| `uv run pytest` | **28 passed** |
| `uv run ruff check app tests` | **All checks passed** |
| `pnpm typecheck` (`tsc -b`) | без ошибок |
| `pnpm test` (Vitest) | **11 passed** (3 файла) |
| `pnpm build` | успешно, `dist/` собран |
| `docker compose config` | успешно (exit 0) |

`docker compose build` в текущем окружении не выполнен: локальный Docker
заменён rootless podman без `/etc/subuid` и `/etc/subgid`, распаковка базовых
образов падает с `potentially insufficient UIDs or GIDs`. Это ограничение
окружения, а не ошибка Dockerfile: синтаксис compose проверен, сборку нужно
повторить на обычном Docker-хосте командой `docker compose up -d --build` и
прогнать `scripts/smoke.sh`.

Frontend-тесты покрывают:

- `QuizForm`: блокировка отправки при неполных ответах, сбор одиночных,
  множественных и открытых ответов, показ серверной ошибки;
- `GradeRubric`: сумма критериев, диапазон балла, обязательный комментарий при
  возврате на доработку, режим без рубрики;
- `format`: проценты, дельты, размеры файлов, ролевые пути и казахские подписи.

Backend-тесты покрывают регистрацию/вход, роли и object-level доступ, CMS,
классы и вступление по коду, назначения, сдачи, автопроверку, проверку
учителем, диагностику и pre/post, CSV, загрузки и аудит.

## 4. Ручной приёмочный прогон

1. `docker compose up -d --build`, дождаться healthy.
2. Гость: главная, ML, STEM, проекты, карточка проекта.
3. Вход учеником → кабинет; попытка открыть `/teacher/dashboard` и
   `/admin/content` — доступ запрещён.
4. Вход учителем → создать класс → код вступления.
5. Вход учеником → вступить по коду дважды → в классе один участник.
6. Учитель: назначить опубликованное задание и диагностику.
7. Ученик: сдать закрытое задание (проверить автобалл), открытое — на проверку.
8. Учитель: проверить работу, вернуть одну на доработку, выставить балл.
9. Ученик: увидеть оценку/комментарий; повторить отправку закрытого задания —
   попытка не должна удвоиться.
10. Пройти pre/post, открыть результаты: пять компетенций и Δ п.п.
11. Учитель: CSV открывается в Excel/LibreOffice, содержит только свой класс.
12. Админ: создать урок, загрузить CSV, добавить Colab-ссылку, опубликовать.
13. Проверить материал в каталоге и на мобильной ширине.
14. Попробовать загрузить `.exe` и файл >25 МБ — понятная ошибка.
15. `docker compose restart` → данные и публикации на месте.
16. `make backup`, затем восстановление на staging по `backup-restore.md`.

## 5. Известные пробелы тестирования

- Нет Playwright/E2E-сценариев «вход → сдача → оценка» в репозитории;
  критический путь проверяется backend-тестами и ручным прогоном.
- Нет нагрузочного тестирования и проверки на Safari/iOS.
- Frontend-тесты покрывают формы и утилиты, но не все страницы CMS.
- Docker-сборка проверяется на тестовом сервере; для CI нужно добавить
  `docker compose build` и smoke-тест.

## 6. Добавление тестов

- Backend: `backend/tests/test_*.py`, используйте существующие фикстуры
  `client`, `db`, `auth_headers`. Для доступа проверяйте не только UI, но и
  прямой API-запрос.
- Frontend: `src/**/*.test.tsx`, Testing Library + Vitest; для сетевых
  сценариев мокайте `fetch` или используйте MSW.
- Перед коммитом: `make check`.
